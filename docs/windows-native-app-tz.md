# ТЗ: Нативное Windows-приложение TRACE (.exe)

## 1. Контекст

Сейчас в настройках тенанта (`components/views/Settings.tsx`, блок «Приложение для Windows») есть
кнопка «Скачать для Windows», которая отдаёт статический `/downloads/TRACE-Setup.exe`
(с именем файла `TRACE-Setup-{subdomain}.exe`). Это Tauri-обёртка (`src-tauri/`, `launcher/`)
— по сути webview, который парсит тенант из имени файла через NSIS-хук
(`installer/hooks.nsh` → `%APPDATA%\uz.trace-os.app\tenant.txt`) и открывает
`https://{tenant}.trace-os.uz/` в системном webview.

**Уточнение:** дизайн НЕ переделываем и с нуля на нативных виджетах не перерисовываем.
Экран в exe должен быть **тем же самым веб-дашбордом TRACE, 1:1**, просто упакованным в
отдельное .exe-окно — не новый UI, не редизайн. Полная переверстка на WPF/нативных контролах
(вариант из раздела 4 ниже) избыточна и не нужна: пользователь должен видеть ровно то же самое,
что и в браузере.

Практически это значит: exe = не системный браузер и не набор нативных окон/кнопок Windows,
а тонкая обёртка (например, .NET + **WebView2**, embedded Chromium-компонент Windows), которая
внутри одного .exe-приложения рендерит тот же самый веб-фронтенд TRACE (тот же React-код,
та же вёрстка, тот же CSS). Отличия от браузера: нет адресной строки/вкладок/меню браузера,
есть свой .exe-файл, свой ярлык, своя иконка — то есть выглядит и ощущается как отдельное
приложение, а не как открытая вкладка Chrome. При этом это не то же самое, что нынешний
Tauri-вариант — Tauri просто редиректил в системный webview на `{tenant}.trace-os.uz` без
контроля токена/окна логина; здесь именно .exe-обёртка со своим окном, иконкой и логикой
хранения токена (см. §3.1), но контент внутри — идентичный веб-дашборд.

Tauri/`src-tauri`/`launcher`/`installer` — вывести из эксплуатации после релиза новой версии
(не обязательно удалять сразу, но новый пайплайн сборки их не использует).

## 2. Цель

Один exe-инсталлятор на тенант, который:
- ставится на ПК ресторана
- при запуске логинится в тот же бэкенд TRACE, что и веб-версия;
- показывает **тот же самый веб-дашборд TRACE без изменений** — весь функционал и визуал
  1:1 с веб-версией, никакого нового дизайна;
- работает **только онлайн** (нет офлайн-режима, нет локального кэша данных) — всегда живой
  запрос к `https://{tenant}.trace-os.uz` / общему API.

## 3. Скачивание — привязка к тенанту

Сохранить механику «скачал → сразу под свой тенант», но без парсинга имени файла хуком инсталлятора:

- Кнопка в `Settings.tsx` должна дёргать backend-эндпоинт вида
  `GET /api/desktop/windows-installer?tenant={subdomain}`, который отдаёт **собранный под этот
  тенант exe** (или единый exe + конфиг, встроенный в файл/подписанный манифест — на усмотрение
  реализации), а не статический файл из `/downloads/`.
- Проще всего технически: единый билд exe + при первом запуске он читает tenant из
  инсталляционного пути/embedded resource, который backend подставляет на лету при скачивании
  (stub-инсталлятор + patch ресурса с subdomain перед отдачей файла). Нужно решение, устойчивое
  к переименованию файла пользователем/браузером (текущий баг Tauri-версии: `" (1)"` в имени файла
  ломает парсинг — в новой версии тенант не должен зависеть от имени скачанного файла).
- Один раз залогинившись, приложение хранит tenant + refresh-токен локально
  (`%APPDATA%\TRACE\`), при следующих запусках не спрашивает повторно.

### 3.1. Пароль спрашивается один раз

- Логин/пароль вводятся один раз при первом запуске приложения на конкретном ПК. После успешного
  логина refresh-токен (long-lived) сохраняется локально в `%APPDATA%\TRACE\` — **зашифрованно**
  через Windows DPAPI (`ProtectedData.Protect`, привязка к пользователю/машине), не plaintext.
- При каждом следующем запуске приложение тихо обменивает refresh-токен на новый access-токен
  и сразу открывает основной экран — без повторного экрана логина.
- Экран логина показывается заново только если: пользователь явно нажал «Выйти», refresh-токен
  отозван/истёк на бэкенде, или файл токена повреждён/удалён.
- Уточнить у бэкенда: TTL refresh-токена и поддерживается ли его revoke/ротация (нужно для logout
  и для случая кражи/переустановки на другом ПК).

## 4. Технологический стек (предложение, подтвердить с СТО)

- **.NET 8 (WinForms или WPF) + WebView2** — одно окно приложения, внутри которого через
  `Microsoft.Web.WebView2` рендерится существующий веб-фронтенд TRACE (тот же билд из `dist/`,
  тот же React-код). Никакого дублирования фронтенда, никакой переверстки под нативные контролы.
- Приложение = тонкий host: своё окно/иконка/ярлык/трей (по желанию), логика логина и хранения
  токена (§3.1), логика привязки к tenant (§3), а весь UI/данные/API-вызовы — то же самое, что
  сейчас крутится в браузере на `{tenant}.trace-os.uz`.
- WebView2 Runtime на Windows 10/11 уже предустановлен в системе в большинстве случаев (входит в
  ОС с 2022) — при отсутствии инсталлятор ставит Evergreen Runtime автоматически.
- Токен/сессия: приложение либо (a) прокидывает сохранённый refresh-токен в веб-страницу через
  WebView2 postMessage/cookie при старте, либо (b) полагается на обычную веб-сессию/cookie внутри
  WebView2 (у него свой персистентный профиль на диске, как у отдельного браузера) — тогда «войти
  один раз» получаем бесплатно от самого браузерного движка, без своей реализации DPAPI-хранилища.
  **Нужно решить это с СТО** — вариант (b) сильно проще и меньше кода.
- Автообновление: обновляется сам host-exe редко (он маленький и стабильный); свежий функционал
  дашборда прилетает сам собой при каждом онлайн-запросе к бэкенду — отдельный updater нужен
  только если меняется сама host-обёртка (иконка, окно, логика логина).

## 5. Функциональный охват

Полный паритет с веб-версией по разделам (see `components/views/*`):
- Дашборд/аналитика ресторана
- Отзывы (Reviews) + AI-инсайты
- QR для официантов + таблица скан/отзывов
- Настройки тенанта (включая этот самый блок с десктоп-приложением)
- Биллинг/подписки (если доступно роли пользователя)
- Мультиязычность (ru/uz/en) — те же переводы, что в `t.*` словарях веба

Роли и права доступа — идентичны веб-версии (владелец/менеджер/сотрудник), эндпоинты те же,
бэкенд не различает клиента (веб или десктоп).

## 6. Нефункциональные требования

- Только online-режим: если нет сети/бэкенд недоступен — понятный экран ошибки с retry,
  никакого офлайн-кэша данных.
- Дизайн: без изменений, это тот же веб-дашборд внутри WebView2 — никакой отдельной темы/палитры
  придумывать не нужно.
- Установка: NSIS или MSIX инсталлятор, ярлык на рабочий стол, автозапуск — опционально
  (уточнить нужно ли автозапускать при старте Windows на кассовых ПК).
- Подпись exe (code signing) — чтобы SmartScreen не пугал пользователей при установке.

## 7. Что нужно решить/уточнить перед стартом разработки (вопросы к СТО)

1. Подтвердить стек: .NET (WinForms/WPF) + WebView2, host-обёртка вокруг существующего веб-фронтенда
   (не переписываем UI нативно).
2. Хранение сессии внутри WebView2: полагаемся на его собственный персистентный профиль/cookie
   (проще) или прокидываем refresh-токен из host в страницу вручную (§4, пункт про (a)/(b))?
3. Механизм привязки тенанта к скачиванию (единый exe + серверный patch ресурса, vs билд на лету
   per-tenant) — тенант не должен зависеть от имени скачанного файла (баг текущей Tauri-версии).
4. Автообновление host-обёртки — нужен ли отдельный update-эндпоинт на бэкенде, или редкие ручные
   релизы достаточны, раз сам дашборд обновляется сам собой (это же веб-контент).
5. Судьба текущего Tauri-стека (`src-tauri/`, `launcher/`, `installer/`) — когда выпиливаем.

## 8. Процесс сдачи

- Вся разработка ведётся в отдельной ветке (`feature/windows-native-app` или аналог) —
  **в `main` не пушить** без ревью.
- Перед сдачей — обязательно протестировать самому (установка/логин один раз/скачивание под
  тенант/работа основного функционала), и **результат тестирования принести вместе с веткой**
  (что проверено, на какой сборке Windows, скриншоты/видео при необходимости).
- Мёрж в `main` — только после ревью и подтверждения, что тестирование пройдено.
